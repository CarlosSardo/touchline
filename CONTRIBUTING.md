# Contributing to Touchline

## Development

Use the Node version in [.nvmrc](.nvmrc) and run `npm ci`. Use a separate local PostgreSQL development target and explicitly migrate/import or seed it before `npm run dev`; startup does not initialize a world. Hosted startup instead requires an explicitly provisioned account registry and permits empty per-user worlds. See [README.md](README.md) for setup, provisioning and save handling.

The approved hobby architecture is self-hosted: one Docker Compose stack on a Raspberry Pi 4 (8 GB, SSD, arm64) with one React + Express app container, one PostgreSQL 18 database and an optional Caddy HTTPS proxy, using multi-arch GHCR images built by the image workflow. The app connects with a non-superuser role that owns the Touchline database; the `postgres` superuser is for administration and backups only, and PostgreSQL is never published beyond loopback. Hosted sign-in is in-app OpenID Connect against the operator's own provider (Authelia on the Pi; redirect URI `https://<host>/auth/callback`). Signing in only proves an identity: a non-admin gets access after an admin (a member of `ADMIN_GROUP`) approves their access request at `/admin`. Never authorize anyone by email, username or display name. Each human has a separate world/save schema selected through `accounts.users`, keyed by `(issuer, subject)` with unique `game_schema`. Keep unrelated external gameplay APIs, telemetry and player faces out of scope.

Approval (or an admin's first sign-in) creates the player's private world schema; the runtime role must never be a PostgreSQL superuser. Keep human account display name/email separate from the fictional sporting director. Do not infer ownership from a director name, profile email, selected SQL schema or a supplied save ID.

## Conflicting Instructions

The Raspberry Pi + PostgreSQL plan supersedes the retired Azure (Container Apps, Azure SQL, EasyAuth) plan and older local-only and SQLite-runtime instructions. GitHub Actions only verifies (manual or pull request) and builds images; deployment stays a manual `docker compose` step on the Pi. Do not add cloud infrastructure, paid services or extra always-on containers. Ask before changing the hosting, cost or authentication constraints.

Work with existing uncommitted changes, including other contributors' changes. Respect assigned file ownership; report a dependency outside your scope instead of editing it. Never revert someone else's work or regenerate a legacy career to resolve a conflict. Preserve SQLite originals and their companions offline; SQLite is neither a runtime nor a current import source.

Before changing a system, read its current implementation and [REQUIREMENTS.md](REQUIREMENTS.md). That document distinguishes implemented gameplay from known realism gaps; update it when those boundaries change.

## Pull Requests

- Keep changes focused and add regression coverage for changed behavior.
- Run the registered `npm run verify` entrypoint locally through `npm run test:local -- npm run verify` (a disposable PostgreSQL 18 container; add `--no-docker` before `--` to use a running loopback PostgreSQL from `SQL_*`): lint, production build, SQL-enabled unit/integration/save tests and browser tests. Install Playwright Chromium first with `npx playwright install chromium`. The [verify workflow](.github/workflows/verify.yml) runs the same suites against a throwaway PostgreSQL container without secrets.
- Account tests run with API, Store and saves in the persistence group of `npm run test:local -- npm run verify -- --parallel`. Local no-auth supplied-Store mode and synthetic principal tests do not prove hosted OpenID Connect isolation. Confirm missing registry, stale schema, valid empty accounts, no-mutation skipped preparation and old-image rejection separately; do not claim deployment or test success without recorded results.
- Use the real SQL schema for integration and browser tests, not SQLite or a reduced persistence substitute. Tests use isolated `touchline_test_` / `touchline_e2e_` schemas. Remote tests require both `SQL_ALLOW_REMOTE_TESTS=true` and `SQL_TEST_DATABASE` matching `SQL_DATABASE`, plus verified TLS; never run tests against the Pi's production database.
- For interface or gameplay workflows, install Playwright Chromium with `npx playwright install chromium` and run `npm run test:e2e`. The browser suite uses separate ports and verifies the target database and isolated schema before mutation. `TEST_URL` must identify a test instance, never any hosted player's world.
- Never run destructive tests against a player's active world. Do not bypass test guards, silently skip unavailable SQL checks, or treat historical SQLite results as proof of SQL compatibility. Report checks actually run, their failures and any untested hosted (Pi, reverse proxy, sign-in) behavior.
- Keep secrets only in the ignored `.env`, never in documentation, tracked configuration, images, logs or test output. Never commit databases, exports, dependencies, generated builds or test artifacts.
- Migration and seed changes need explicit review. Inventory legacy sources first; conversion requires `--apply --yes`, and replacement requires a new backup path. Seed only a new empty database, never an existing career. Do not delete original databases, snapshots or sidecars after conversion.
- Manual approval is the reviewed provisioning path: register the OpenID Connect client at the provider, keep the OIDC and session secrets only in `.env`, create the registry with `accounts:migrate -- --apply --yes`, deploy, then approve access requests at `/admin`. Do not hand-add players to the registry or authorize them by email; operators must not bypass the registry. Apply world migrations with `db:migrate -- --registered --apply --yes`.
- Back up with `scripts/pi-backup.sh` before every upgrade or migration. Roll back by restoring that backup with `scripts/pi-restore.sh`, never by running an older image against migrated data, deleting the registry, weakening sign-in or reseeding.
- Preserve replay compatibility when changing match rules. Version match snapshots instead of changing the interpretation of historical fixtures.
- Schema changes are numbered world migrations appended to `schemaMigrations` in [server/sql-schema.ts](server/sql-schema.ts): version 1 is the baseline, 2 narrows `players` rows, 3 adds the GBE evidence tables, 4 adds player and competition registrations, 5 adds the club-offer index, 6 adds `sanctions`, 7 adds `club_projects` and the world-feed index, 8 adds `owners`, `club_ownership` and `ownership_events`, 9 adds `player_honours`, `player_injuries` and `player_milestones`, 10 adds the top-scorer index, and 11 adds the indexed `players.height`/`players.weight` copies of the profile. Take the next free number (12), keep the array sorted by version, never edit a migration that has shipped, and keep statements idempotent (`IF NOT EXISTS`). `Store.schema()` refuses a database migrated by a newer version, and save checkpoints expect every version applied. Live careers receive migrations through `db:migrate -- --registered`, so any backfill runs in the migration or lazily on first use; never require a new world. Add a new world table to `WORLD_TABLES` (and `IDENTITY_TABLES` if it has an identity column), and to `ADDED_WORLD_TABLES` so older checkpoints that lack it still import. Data that does not need a table goes into existing JSON columns (release and relegation clauses in the player contract, part-exchanges in `negotiations.data`, directors' policies and administration in `clubs.data`) and is backfilled lazily, once and idempotently, like `ensureOwnership`, `ensurePlayerRecords` and `ensureReleaseClauses`; anything generated for an older world must be deterministic from the world seed so it matches a new world. Add tests that migrate an existing world and import an older checkpoint.
- [server/eligibility.ts](server/eligibility.ts) is the single source of truth for signing and eligibility: `canSign` (transfer rules only, never GBE or quotas), association and competition registration, `eligibleForFixture` / `competitiveRegistrationSql` for match selection, and `reevaluateRegistrations`. The badge labels are pure functions in [shared/eligibility.ts](shared/eligibility.ts). Call these instead of adding registration, GBE or quota checks to individual signing, loan or selection paths, and extend [server/eligibility.test.ts](server/eligibility.test.ts) when the rules change.
- AI clubs read their situation from the daily club policy snapshot in [server/club-policy.ts](server/club-policy.ts) (`clubPolicySnapshot`, or `marketSnapshot` for the market): squad depth and needs by position and age, surplus, transfer budget, wage room, FFP headroom, embargo, director-of-football policy and owner. It is built once per world and day in process (the market applies its own moves to it in memory) and is shared by the world market, club offers, rival bids, deal clauses and club life. Extend it instead of adding per-club or per-attempt queries to a daily pass, and call `forgetClubPolicies` when a world is replaced in the same process.
- Publish AI clubs' activity only through the world feed in [server/world-news.ts](server/world-news.ts): publish with `worldNewsBatch` (one insert per pass; `worldNews` for a single item) and a kind for the feed's filter (for example `transfer`, `loan`, `contract`, `affiliate`, `project`, `director`, `manager`, `ownership`, `sanction` or `administration`; labels in [src/ClubLife.tsx](src/ClubLife.tsx)). These `Worldwide` items stay out of the director's inbox; use `news()` only for events that concern the director's own club.
- Changes that write more per simulated day must stay within the storage budgets in [server/check-simulation.ts](server/check-simulation.ts). The season soak (`npm run test:local -- npm run simulation:check -- --seasons=1`, which the verify workflow runs for 3 seasons by default) fails when `players` exceeds `PLAYER_ROW_BUDGET_BYTES` (10 KB per row) or the other tables grow beyond `seasonBudgetMB` in a season. The first season after generation may use `FIRST_SEASON_FILL` (1.75) times the budget, because it fills the rolling tables to their steady size. Fix the growth instead of raising a budget without review. Run a soak against a database no other session is using: another client holding a snapshot (a long or idle-in-transaction session, a test run, another soak generating its world) stops VACUUM from reclaiming the `players` table's dead row versions, so the footprint check measures bloat rather than the world. The soak prints a _Footprint caveat_ when it saw such sessions; rerun it alone before trusting or tuning a budget. The soak also prints market metrics per season (moves per club by tier against `MARKET_TARGETS`, loan, free-agent and deadline-day shares, FFP breaches and sanctions); these are reported, not enforced, so check them when changing the market. Keep daily passes set-based and bounded, and measure per-day cost on the full world before and after. `/api/advance` commits each day separately: do not wrap multiple days in one transaction.
- Include a brief description of the behavior changed, the checks run and any remaining limitations.

## Bug Reports

Open a [GitHub issue](https://github.com/CarlosSardo/touchline/issues) with reproduction steps, expected and actual behavior, Node/browser versions and the in-game date. Include relevant error messages, but do not upload personal saves or credentials by default.
